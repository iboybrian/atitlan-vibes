# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Atitlán Vibes — a mobile-first travel/events app for the Lake Atitlán towns (Guatemala). React 19 + Vite SPA, Supabase backend, wrapped for Android via Capacitor. UI copy is English; README/docs are Spanish.

## Commands

- `npm run dev` — Vite dev server at http://localhost:5173
- `npm run build` — production build to `dist/`
- `npm run lint` — ESLint (flat config, `eslint.config.js`)
- `npm run preview` — serve the built `dist/`

Android (Capacitor): `npm run build && npx cap sync` after web changes, then `npx cap open android`. `webDir` is `dist/`, appId `com.atitlanvibes` — this is the package name reserved on Play Store and can never change.

Supabase Edge Function: `npx supabase functions deploy notify-town`. Full setup (secrets, DB webhook, testing) in [supabase/functions/notify-town/README.md](supabase/functions/notify-town/README.md).

No test runner is configured.

## Environment

Requires `.env` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Read via `import.meta.env` in [src/lib/supabase.js](src/lib/supabase.js). Without these the app renders blank (session fetch hangs).

## Architecture

Routing is flat in [src/App.jsx](src/App.jsx): all routes nest under one `<Layout>` (`/`, `/map`, `/plans`, `/alerts`, `/town/:id`, `/town/:townId/chat`, `/event/:id`, `/auth`, `/reset-password`, `/profile`, `/settings`, `/about`, `/privacy`, `/admin`; `/favorites` redirects to `/plans`). Deployed as an SPA — [vercel.json](vercel.json) rewrites all paths to `index.html`.

**Every route is wrapped in `RequireAuth` except `/auth`, `/reset-password`, `/privacy`, and the guest-browsing routes `/`, `/map`, `/town/:id`, `/event/:id`** — no session redirects to `/auth`. Guests on those see only events where `isTodayOrTomorrow()` ([utils.js](src/lib/utils.js)) holds, followed by a `LoginNudge`. Post-your-vibe, the town WhatsApp-group button, Save (heart or swipe right), Going / Check in, and the My Plans and Alerts tabs are greyed out and call `askLogin()` (from `useOutletContext()`, or a prop on TabBar), which shows Layout's login toast. The organizer WhatsApp on an event stays usable on purpose. The today/tomorrow limit is client-side only: the anon key can still read every approved event ([20261019010000_guest_read.sql](supabase/migrations/20261019010000_guest_read.sql)). That's acceptable for public listings; move it to RLS if it ever isn't. `/privacy` stays public on purpose: Play Store review has to reach the policy without an account. `/reset-password` is public because the recovery session may not exist the instant the page renders (see PKCE notes below) — it handles the no-session case itself rather than relying on `RequireAuth`. Any new public page needs the same exemption.

**Auth & global state** live in a single React context, [src/context/AuthContext.jsx](src/context/AuthContext.jsx) (`useAuth()`). It owns the Supabase session, the joined `userProfile` row, and dark mode. Two things to know:
- `AuthProvider` renders `{!loading && children}` — the whole app is gated on the initial `getSession()` resolving. A broken/missing Supabase env means nothing paints.
- `session` (auth) and `userProfile` are separate. `userProfile` is *not* the whole `users` row — the context selects only `name, house_affinity, avatar_url`. Anything else (phone, `current_town_id`, push fields) has to be queried by the page that needs it. After editing the profile, call `refreshProfile()` or the header/avatar goes stale.
- Dark mode is a `dark` class on `<html>` persisted to `localStorage`, matching Tailwind's `darkMode: 'class'`.

**Auth redirects (OAuth + password reset)** — the client runs on `flowType: 'pkce'` ([supabase.js](src/lib/supabase.js)), so every redirect comes back as a one-shot `?code=` instead of tokens in the URL. Three consequences worth knowing before touching any of it:

- **Native can't use `window.location.origin`.** In the APK that's `https://localhost`, which isn't in Supabase's Redirect URLs, so Supabase silently falls back to the dashboard Site URL and the user lands on the web app. Native redirects go to the `com.atitlanvibes://auth` deep link instead — declared in [AndroidManifest.xml](android/app/src/main/AndroidManifest.xml), listed in the dashboard allow list, and branched on `isNative()` at the call site.
- **The deep link is handled in [main.jsx](src/main.jsx), not in React.** Capacitor kicks Google out to the system browser; the intent comes back through `appUrlOpen`, never through the WebView's URL, so `detectSessionInUrl` can't see it and the listener calls `exchangeCodeForSession()` by hand. It's registered at module scope on purpose — a cold start from the intent would outrun a `useEffect`.
- **`PASSWORD_RECOVERY` is never emitted under PKCE.** Recovery and Google login both notify `SIGNED_IN`; the only thing telling them apart is `data.redirectType === 'PASSWORD_RECOVERY'` off the exchange call, which is why native forwards to `/reset-password` itself. On web that field comes back null and the path *is* the signal — hence `redirectTo` pointing at `/reset-password` there. Never gate recovery UI on the event.

PKCE also ties the reset link to the browser that requested it (the `code_verifier` lives in its storage), so the copy tells users to open it on the same device. Email *confirmation* is unaffected: Supabase confirms the address server-side before redirecting, and the sign-up copy already says to log in manually afterwards.

**Data layer** is direct Supabase calls from components/pages — no API layer, no data-fetching library. Most pages do their own `supabase.from(...)` in a `useEffect`. Two lists are shared instead, as a cached *promise* so components that mount together make one request: towns ([towns.js](src/lib/towns.js), `useTowns()`) and every approved upcoming event across all towns ([events.js](src/lib/events.js), `useEvents()`, refetched after 5 min because Layout never remounts on Android). Now, Map, the town sheet's counts, Alerts and the tour all read `useEvents()`; don't add a second copy of that query. Tables in use: `users`, `towns`, `events`, `event_favorites`, `event_attendance`, `chats`, `messages`, `message_reactions`. Events are gated on `is_approved`; `is_feature` events go to the front of the Now deck (that placement is what promotions pay for). Storage buckets: `avatars` (profile pics), `logo`. Only part of the schema and RLS is versioned, under [supabase/migrations/](supabase/migrations/); the base tables live in the dashboard.

**An event's date is computed, not stored.** `events.recurring_days` (`smallint[]`, `0` = Sunday, `null` = one-off) says which weekdays a series repeats on, and `calendar_date` becomes the date the *series started* — usually months in the past. The date that matters is `nextOccurrence()` in [utils.js](src/lib/utils.js), worked out at read time. Three consequences:
- **Never sort or filter on `calendar_date` alone.** A weekly event would sort by its start date and sink below everything. `compareEventsByWhen()` sorts on the computed date; the query in [events.js](src/lib/events.js) has to `.or(...recurring_days.not.is.null)` or the `.gte()` hides exactly the events that are on every week, and it sorts in JS because no column can express the order. The Now-page helpers (`timeFilter`, `startsIn`, `dayGroup`) all go through `nextOccurrence()` for the same reason.
- **Weekday maths is UTC-only** (`Date.UTC` + `getUTCDay`). `new Date('2026-08-30').getDay()` reads the runner's timezone and lands a day early west of Greenwich. `todayInGuatemala()` is the opposite case and is pinned to `America/Guatemala`, not the device: the events happen here regardless of what a traveller's phone thinks. Run `npm run check` under a couple of `TZ=` values — that is the whole point of those scripts.
- **This is deliberately not a cron.** A nightly job rolling `calendar_date` forward takes every recurring event down the first night it fails, silently, and `+7` is wrong for a Mon/Wed/Fri event anyway.

The one scheduled piece is [`purge_past_events()`](supabase/migrations/20260904010000_purge_past_events.sql) — pg_cron, 06:30 UTC, hard-`DELETE`s one-off events more than 7 days past. It has three guards (`recurring_days is null`, `calendar_date is not null`, the 7-day grace) and all three are load-bearing. `event_favorites` cascades, so this also removes the event from users' saved lists; it is irreversible, and the grace window is the only net.

**The `users` row is created by a Postgres trigger, not by the client.** `handle_new_user()` ([20260805000000_add_phone.sql](supabase/migrations/20260805000000_add_phone.sql)) fires on `auth.users` insert and copies name/phone out of `raw_user_meta_data`. It has to work that way: with email confirmation on, `signUp()` returns no session, so the client cannot insert into `public.users` itself. Adding a sign-up field means passing it in `signUp({ options: { data } })` *and* editing that function in a new migration. Google sign-ups never see the email form, so `phone` stays null for them.

Supabase's confirm-signup email template is mirrored at [supabase/templates/confirm-signup.html](supabase/templates/confirm-signup.html) — git copy only, nothing reads it. Editing it does nothing until it's pasted into Authentication → Emails in the dashboard.

**Admins & event review** — user submissions land as `is_approved = false`. Admin rights are `users.is_admin`, set by hand in the dashboard and enforced by RLS through `is_admin()` ([20261019000000_admins.sql](supabase/migrations/20261019000000_admins.sql)). Users can update their own `users` row, so the `protect_is_admin` trigger rejects any `is_admin` change made as `anon`/`authenticated`. Don't drop it, or anyone can promote themselves from the console. `useAuth().isAdmin` only shows or hides UI. [Admin.jsx](src/pages/Admin.jsx) (`/admin`) lists pending and approved events with the submitter's name and phone, and can approve, edit, or delete them. Approving is a plain `is_approved` update, so the existing trigger announces the event to its town.

**"Current town"** is the single explicit choice the user makes ([TownPicker.jsx](src/components/ui/TownPicker.jsx), the pill in the header). It writes two places: `localStorage.current_town` via `pickTown()` in [towns.js](src/lib/towns.js) — so it works logged out — and `users.current_town_id` when signed in. Read it with `useCurrentTown()`, not the DB and not a bare `getCurrentTown()`: the pill lives in Header and the pages it scopes (Now, Map, Alerts) are siblings, so only the subscribed hook re-renders them. The stored value is `{id, name}` only; take coordinates from `useTowns()`.

**Picked town vs. detected town are different columns and must stay that way.** `current_town_id` is a stated preference and drives everything the user *sees*. `users.detected_town_id` is where geolocation last placed them and only affects *who push targets*. Never let one overwrite the other: hijacking the picker would yank a user who deliberately chose San Marcos back to wherever their phone is.

For *targeting*, both count and the rule lives in one place — [supabase/functions/notify-town/targeting.js](supabase/functions/notify-town/targeting.js), plain `.js` so Deno and the bare-node check (`npm run check`) share one source of truth. A detection counts for 72h, a pick for 7 days (`current_town_set_at`, stamped by TownPicker). The one asymmetry is deliberate: **an expired pick still counts unless a fresh detection contradicts it** — a user with location off has no other signal, and a rule that mutes them entirely is worse than one that occasionally notifies someone who moved. Changing either window changes who got paid-for reach, so change it there and nowhere else.

**Geolocation** ([src/lib/geolocation.js](src/lib/geolocation.js)) is native-only and foreground-only, and mirrors `pushNotifications.js` export for export (`isLocationSupported` / `getLocationPermissionStatus` / `setLocationPreference` / `refreshDetectedTown`). Three things not to undo:
- **Coordinates never leave the device.** `nearestTown()` in [utils.js](src/lib/utils.js) snaps a fix to the closest town client-side and only the town id is stored. That's the whole privacy claim, and the Play Data Safety answers depend on it. Never add a lat/lng column or send coordinates to an Edge Function. `utils.js` also **imports nothing**, which is what lets `npm run check` run it under bare node — keep it import-free.
- **No background location, ever.** `ACCESS_BACKGROUND_LOCATION` is the one thing that triggers Google's Location Permissions declaration (justification + demo video + weeks of review). The manifest also strips `ACCESS_FINE_LOCATION` with `tools:node="remove"` because the Capacitor plugin's own manifest would otherwise merge it in — verify the *merged* manifest after `npx cap sync`, not the source one.
- **Two gates, not one.** `refreshDetectedTown()` requires the OS permission *and* `users.location_enabled`. Android keeps reporting `granted` after the user flips the Settings toggle off, so without the DB flag the toggle would silently undo itself on the next app open. `Layout` also registers an `appStateChange` listener because the shell does not remount on resume.

**Going / Check in** — `event_attendance` ([20261031000000_event_attendance.sql](supabase/migrations/20261031000000_event_attendance.sql)) holds one row per user per event, `status` `going` or `checked_in`. RLS lets you touch only your own rows. Other people's attendance is read **only** through the `event_going(ids)` RPC ([going.js](src/lib/going.js), `useGoing()`): it is `security definer` so it can read `users`, and returns a count plus up to five `{name, avatar_url}`, with no faces at all for a guest. Never open a select policy on `users` or `event_attendance` to get faces instead — `users` rows hold phone numbers. Check in is only enabled on the day (`happeningToday`) and has no location check, because coordinates never leave the device (see Geolocation). The privacy policy says who sees a Going; keep it true if this changes.

**Map** — [TownMap.jsx](src/components/ui/TownMap.jsx) is plain Leaflet in an effect (no react-leaflet) on OpenStreetMap's public tiles, with one pin per town at `towns.lat/lng`. Events have no coordinates, so pins are per town and "Take me there" on the event page hands Google Maps the venue name instead. The wrapper is `isolate` because Leaflet's panes carry z-index 400-1000 and would otherwise paint over the sticky chrome. If OSM ever refuses the APK's `https://localhost` referer, swap the one tile URL there.

**Realtime chat** — [src/pages/ChatRoom.jsx](src/pages/ChatRoom.jsx) subscribes to Postgres changes via `supabase.channel('messages-<chatId>')` and `reactions-<chatId>`. One `chats` row per town; messages and reactions hang off it.

**Push notifications** — native only, end to end. Web push is deliberately off: `isPushSupported()` in [src/lib/pushNotifications.js](src/lib/pushNotifications.js) returns `isNative()`, so in a browser the soft prompt never shows and no token is written (`public/sw.js` is dead weight kept for a future real VAPID setup).

- Client: Capacitor `@capacitor/push-notifications` gets an FCM token, stored on `users.push_token` / `push_enabled`. `register()` resolves *before* the token exists — it arrives on the `registration` event — so `registerForToken()` attaches listeners first and settles from there, with a 10s timeout. FCM rotates tokens, so `refreshPushToken()` runs on every mount of [Layout.jsx](src/components/layout/Layout.jsx) and silently no-ops unless already opted in.
- **Tapping a push opens `/event/:id`, and that is split across two files for a reason.** `startPushTapListener()` is called at module scope in [main.jsx](src/main.jsx) — a tap can cold-start the app and the plugin fires while Android is still building the activity, so a listener registered in a `useEffect` misses it (same race as the OAuth deep link). It buffers the id; `onPushTap()` in `Layout` claims it once the router exists. Don't collapse these into one `useEffect`.
- Server: [supabase/functions/notify-town/index.ts](supabase/functions/notify-town/index.ts) (Deno Edge Function). It mints a Google OAuth2 token from a service-account JWT and posts to FCM HTTP v1 token by token — there is no topic API in the Capacitor plugin — and nulls tokens that come back `404 UNREGISTERED`. Two entry points, told apart by whether the payload has a `record`:
  - **Webhook** on `events` INSERT+UPDATE. Notifies once, on the approval transition (new row already approved, or `is_approved` flipping false→true). An INSERT that is *not* approved is a user submission: it goes to every `users.is_admin` instead, as a full email through Resend (`RESEND_API_KEY`; skipped with a log if unset) plus a push (`data.route = '/admin'`, ignores `push_enabled`). Taps go through `pushPath()` in pushNotifications.js, which maps `data.route` or `data.eventId` to an in-app path.
  - **Manual `{ "eventId": N }`**, the paid-promotion path. Skips the announce-once gate deliberately (that gate stops an *edit* re-notifying; a promotion isn't an edit) but 404s if the event doesn't exist. **It accepts only an event id — never an operator-supplied title or body.** That's what keeps every push app content that opens a real event, rather than advertiser copy delivered through a system notification, which Play's Ads policy restricts. Don't add that parameter.
- Recipient selection is one over-fetching query plus a predicate in TS, not a PostgREST filter: nested `and()`/`or()` strings are unreadable and a typo silently changes who got paid-for reach.
- The soft-prompt (`PushPromptModal`) fires 2s after first login, gated by a `localStorage` flag, and asks for push *and* location in that order — the copy before the OS dialogs is the Play prominent disclosure. Its key is versioned (`push_prompt_shown_v2`); bump it again if the prompt ever asks for something new, or existing users never see it.

**In-app updates** — [src/lib/appUpdate.js](src/lib/appUpdate.js) (`@capawesome/capacitor-app-update`, pinned) asks Google Play on launch and every resume whether a newer version is out; Layout shows a banner that runs a *flexible* update (background download, then "Restart"). Play priority ≥ 4 skips the banner and forces Play's full-screen *immediate* update — priority is only settable through the Play Developer API, not the Console UI. Only works on installs from Play (internal testing counts); a sideloaded/debug APK always reports no update. Bump `versionCode` in [build.gradle](android/app/build.gradle) on every upload — that number is what Play compares.

**Ad attribution (Meta App Events)** — Android only, native only, no JS. `facebook-core` (not the umbrella SDK) in [app/build.gradle](android/app/build.gradle); [AndroidManifest.xml](android/app/src/main/AndroidManifest.xml) carries the `com.facebook.sdk.*` meta-data and the SDK's `FacebookInitProvider` boots it before `MainActivity`, so there is no init code. Things not to undo:
- **It brings permissions the manifest never lists.** `AD_ID` and `ACCESS_ADSERVICES_*` arrive by merge, so Play Console "Advertising ID = yes" and the Data Safety form must stay in step with it; check the *merged* manifest after any SDK bump. The privacy copy (`privacy.noTracking` / `privacy.adMeasurement`) also admits this SDK — removing the SDK or adding new data to it means editing that copy.
- `facebook_client_token` in `strings.xml` is a placeholder until the user supplies the real one; the App ID is public and committed.
- No Facebook Login, so no key hashes / `fb_login_protocol_scheme`. Never add the `facebook-android-sdk` umbrella just to get events.
- **Custom events go through [metaEvents.js](src/lib/metaEvents.js) → `MetaEventsPlugin.java`** (a local Capacitor plugin, registered in `MainActivity` *before* `super.onCreate`). Every helper is fire-and-forget, no-ops off native, and never throws, so call sites are bare one-liners. Params are opaque ids / enum words only: JS `clean()` and the Java allowlists both drop any value that isn't `[A-Za-z0-9_-]{1,64}` (that rejects emails, names, message text, coordinates) and any event or param key not on the list. New event or key = edit both allowlists and the `privacy.adMeasurementBody` copy. Events: `fb_mobile_complete_registration` (Auth email sign-up; Google first login in main.jsx), `login` (Auth email; Google in main.jsx), `fb_mobile_content_view` (TownDetail / EventDetail), `fb_mobile_add_to_wishlist` (EventDetail favorite on), `open_town_chat` (ChatRoom mount; `click_whatsapp_chat` is the separate event for the TownDetail WhatsApp FAB tap, `town_id` only), `send_chat_message` (ChatRoom, id only), `set_current_town` (TownPicker `choose`, not the hydrate effect), `enable_push` (`savePushToken`). No location or share events, by decision.
- TODO (user decision, later): consent prompt / opt-out. Collection is deliberately always-on for now; see the `AutoLogAppEventsEnabled` / `AdvertiserIDCollectionEnabled` flags in the manifest.
- The SDK must never be given coordinates, emails, or other PII — same line as the geolocation privacy claim.

## Conventions

- **One responsive shell, one width declaration**: everything renders inside a centered column that steps 450 → 576 → 672 → 896px across `sm`/`md`/`lg` ([src/components/layout/Layout.jsx](src/components/layout/Layout.jsx)). That line is the *only* place the shell width is written — child chrome inherits it, so never hardcode a shell width elsewhere.
- **Chrome uses `sticky`, not `fixed`**: `fixed` resolves against the viewport, so on tablet it detaches from the shell and stretches into the gutter. The tab bar ([TabBar.jsx](src/components/layout/TabBar.jsx)) is `sticky bottom-0` as the column's last flex child, and hides itself on `/event/:id` (whose own sticky Going bar takes its place) and on chat. The town-chat FAB ([TownDetail.jsx](src/pages/TownDetail.jsx)) is a `sticky bottom-24 flex justify-end h-0 pointer-events-none` row. Reuse those patterns for any new pinned UI. Centered overlays (modals, the Profile toast) and bottom sheets ([Sheet.jsx](src/components/ui/Sheet.jsx), capped at `max-w-lg`) may stay `fixed` — viewport-anchored equals shell-anchored. Sheet portals to `<body>`: opened from inside the sticky Header, its z-50 would be trapped under Header's z-40 stacking context and the tab bar would cover it. The shell is `overflow-x-clip` (not `hidden`, which would break sticky) so the menu drawer can park off its right edge.
- **z-index tiers**: chrome (Header, TabBar, the event page's Going bar) is `z-40`; modals and the Sidebar are `z-50` and must cover chrome. Don't raise chrome.
- **Safe-area insets**: `index.html` sets `viewport-fit=cover` because Android 15 (targetSdk 36) forces edge-to-edge — the WebView draws under the status and gesture bars. Chrome pads itself: Header `pt-[env(safe-area-inset-top)]` with `box-content`, TabBar and the Going bar `pb-[calc(…+env(safe-area-inset-bottom))]`, sheets the same. Any new pinned UI needs it too.
- **Grids reflow**: event card grids are `grid-cols-2 md:grid-cols-3 lg:grid-cols-4`. Prose/form pages (Profile, Settings, About, EventDetail) cap their own content at `max-w-2xl mx-auto` rather than stretching to the full shell.
- **Tailwind brand tokens** ([tailwind.config.js](tailwind.config.js)): `turquoise` `#00CED1`, `sunflower` `#FFB800`, `bg` `#F5F5F0`. Use these, not raw hex.
- **Images**: run any user/DB-supplied image URL through `getDirectImageUrl()` ([src/lib/utils.js](src/lib/utils.js)) — it rewrites Google Drive / Dropbox share links to direct-embed form and falls back to a placeholder.
- **Lint gotcha**: `no-unused-vars` ignores `^[A-Z_]` — capitalized/underscore identifiers won't flag as unused.
- **`android/app/google-services.json` stays committed** — it is Firebase *client* config, not a credential; without it the Gradle plugin skips and push breaks. The Firebase *service account* key is the secret: `.gitignore` blocks `*-service-account*.json` / `serviceAccountKey*.json`, and it belongs only in `supabase secrets`.
